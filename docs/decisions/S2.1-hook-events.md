# S2.1 — What do Claude Code's hooks really report, and what state does each sequence imply?

Date: 2026-11-04 · Status: decided

## Decision

Keep hooks as the only source of Claude's state, with the `--settings` file and handler forms from TECH_SPEC §4.2, which all worked on Windows. Change the reducer in three ways, because the provisional table was wrong in each:

1. **A `Stop` must not clear a background agent's pending permission.** Otherwise voice text can approve that permission. This is the main finding.
2. **Denying a permission fires no hook at all,** so `awaitingPermission` must not rely on one to end.
3. **`idle_prompt` did not arrive after an Esc,** so after an interrupt or denial, voice comes back only through a later turn or "Re-arm voice".

The corrected table is in TECH_SPEC §4.3. Recorded sequences are in `desktop/test/scenarios/`.

## Evidence

Run with `node spikes/S2.1/run.mjs <output folder> <project folder> [scenarios]`, which drives real `claude` through `node-pty` with the hook config from §4.2. `spikes/S2.1/trust.mjs` opens a visible window for the manual trust check. One run per scenario, and times come from these single runs. The harness runs on Haiku.

### Recorded sequences

| Scenario | Hooks, in order |

| `/clear` | `SessionEnd(clear)` `SessionStart(clear)`, 60 ms apart. No `UserPromptSubmit` |

### The safety hole

In the last row, `PermissionRequest` came 115 ms **before** `Stop` (77 ms in a second run). Under the provisional table that means `awaitingPermission`, then `idle`, with the prompt on screen. The next signal is `permission_prompt`, about 6 s later.

`agent-permission-send` tested what a send does in that state: a paste of a prompt, then Enter. The pasted text was discarded and **Enter approved the agent's write**: `PostToolUse` came 214 ms later, and `agent-write.txt` exists. The prompt defaults to "Yes", so a voice send into it approves it.

### `idle_prompt`

| After | Result |
| --- | --- |
| A normal `Stop` | `idle_prompt` 60.0 s later |
| Esc at a permission prompt | Nothing within 75 s |
| Esc mid-turn | Nothing within 75 s |

The hooks reference suggested `idle_prompt` would end `unknown`. Each was seen once, and it may come later than 75 s, but nothing can rely on it.

### Local UI

None of these fires a hook when opened or left. An Enter that opens one fires nothing, so it raises `localUiSuspected`, as §4.4 planned.

| Screen | Typed text | Pasted text | Enter |
| --- | --- | --- | --- |
| `/model` | "hello": no visible effect. The menu says `s` means this session only, and models are numbered, so those keys likely act | No visible effect | **Not tested.** It says "set as default", which would change the user's settings |
| `/resume` | Goes to the search box, as far as the screen capture shows | No visible change captured | Resumes the highlighted session |

Pasting is safe in all of them, but Enter is not, and delivery sends both. So the gate has to hold in every one.

### Trust and first run

| Check | Result |
| --- | --- |
| Never-trusted folder, 31 minutes at the prompt | No hooks |
| After a person accepted | `SessionStart`, then `SessionEnd` on `/exit` |
| Folder under an already-trusted parent | No prompt at all: trust is inherited |
| First-run theme and login screens, in an empty `CLAUDE_CONFIG_DIR` | No hooks |

So `starting` holds on all of them. Nothing here logged in or accepted trust automatically.

### Values confirmed

| Item | Result |
| --- | --- |

| `http` hooks with `$VOICEUP_HOOK_TOKEN` | Work; no 401 in any run |

| `Stop` body | Has `background_tasks`, a list |

### Not observed

- **A foreground subagent.** Every `Agent` call returned in about 50 ms with `background_tasks: 1`, even when asked for `run_in_background: false`. The `busy` rules should cover one, unconfirmed.
- **`/model` + Enter**, and the later login steps, on purpose.
- **`elicitation_dialog`.** The dialog was answered after 2 s, so a later notification wouldn't have had time to fire.
- **Auto-compaction mid-turn.** Only manual `/compact` was run.
- **`SessionEnd` isn't reliable on quit.** Ctrl+C twice right after `Stop` produced no `SessionEnd` within 5 s in five runs. That may be the harness's timing, so `exited` comes from the PTY.

### Settings that stop hooks (measured in S2.3)

| Setting in `.claude/settings.local.json` | Result |
| --- | --- |
| `disableAllHooks: true` | No hooks at all |
| `allowedHttpHookUrls: []` | `SessionStart` still fires, through its command hook. Each http hook prints "HTTP hook blocked" on Claude's screen |

`/hooks` can't confirm our hooks. It reports "33 events · 0 with hooks" and "No hooks configured for this event" during a session where they fire, and Claude's own "running Stop hook" spinner shows.

## Environment

Windows 10 Home 19045, Ryzen 5 3600. Claude Code 2.1.318 (npm install, through `claude.cmd`), Haiku 5.5, permission mode default. Node 24.21.0, `node-pty` 1.2.0-beta.18. Not in Electron: the question is what Claude sends, not how the app receives it.

## Consequences

- **S2.3:** `SessionEnd` was recorded here but is not registered in the app: with it, closing the app took 9.6 s and was force-killed (§4.2). The scenarios keep it as a record of what Claude sends.
- **S2.2:** `test/fake-claude.mjs` replays `desktop/test/scenarios/*.json`. Each entry is a hook event with its body, or an `input` or `ptyExit` step. A body's `prompt` is `prompt text`, or the tag if Claude sent a tag, since fixtures are public.
- **S2.4:** implements the corrected §4.3, including pending agent permissions and `turnActive`. `agent-permission-send` must be a replay test that ends in a blocking state at every step.
- **S2.5:** "Re-arm voice" is the normal way back after an Esc, not a rare fallback, so it has to be easy to find.
- **S5.4:** a `UserPromptSubmit` whose prompt is a Claude tag such as `<task-notification>` is not confirmation of a delivery (§4.5).
- **S5.1:** no change to the gate; the fix is in the state it reads. Copied into TECH_SPEC §4.3, §4.4, §4.5 and §11.
- **Cosmetic:** Claude's spinner shows "running Stop hook" briefly. It's how Claude shows any hook, and nothing changes in its behaviour.

## Rejected options

- **Treat `Stop` with `background_tasks > 0` as not idle.** A background agent can run for a long time with no prompt open, and voice should work then. Blocking only on a pending permission keeps that.
- **Clear `awaitingPermission` on a timer after a denial.** The spec forbids guessing `idle`, and a timer can't tell a denial from a person still reading the prompt.
- **Read the screen to detect prompts.** §4 rules out screen parsing, and it would break on any Claude UI change.
- **Pasting without Enter, then a second confirmation.** It doesn't help: the danger is the Enter, and sending needs one.
