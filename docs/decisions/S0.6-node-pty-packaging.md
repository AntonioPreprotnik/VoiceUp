# S0.6 — Does `node-pty` build and load inside packaged Electron on Windows?

Date: 2026-11-02 · Status: decided

## Decision

Use `node-pty` **1.2.0-beta.18**, pinned exactly, from its **bundled prebuilds with no rebuild**: set `npmRebuild: false` and add no `install-app-deps` postinstall. Visual Studio Build Tools and Python are no longer a dev-machine requirement. S1.1 must handle the rejected promise that every `kill()` produces under the `runAsNode: false` fuse.

## Evidence

Every run is a packaged `--dir` build with `asar` on and all five fuses set as in `desktop/electron-builder.yml`, except variant b. Each run: load, `cmd.exe /c echo` read back through the PTY, type into an interactive `cmd.exe`, resize, `kill()`, a grandchild `ping`, a grandchild `node` that ignores SIGHUP, SIGINT and SIGTERM, then 100 spawn/kill repeats (20 for b and c).

| Variant | Machine | Rebuild | Result | Notes |
| --- | --- | --- | --- | --- |
| a: 1.1.0 | Dev PC, no Visual Studio | off | **pass** | 8–9 MB unpacked |
| b: 1.1.0, `runAsNode` fuse on | Dev PC | off | pass | Baseline. The forked helper starts but exits 1 after 126 ms, with no answer |
| c: 1.1.0, `useConptyDll: true` | Dev PC | off | **fail** | Typed output never seen, `kill()` to exit 862 ms, exit code 1. Cause not investigated |
| d: 1.2.0-beta.18 | Dev PC | off | **pass** | 7.0 MB unpacked |
| f: 1.1.0 | Dev PC | **on** | **build fails** | `Could not find any Visual Studio installation to use` |
| t: 1.2.0-beta.18, trimmed | Dev PC | off | **pass** | 2.9 MB unpacked |
| ci1: 1.2.0-beta.18 | `windows-latest` | off | **pass** | [CI run](https://github.com/AntonioPreprotnik/VoiceUp/actions/runs/41486039122) |
| ci2: 1.2.0-beta.18 | `windows-latest` | **on** | **pass** | Same run. Compiled `build/Release/*.node` confirmed present |

**Rebuild is not needed.** Prebuilds pass with no compiler on the machine. Building with electron-builder's default `npmRebuild: true` fails without Visual Studio even though the prebuilds work, so the setting has to be off. A compile from source does work on `windows-latest` if we ever need it.

**`kill()` under the fuse.** Measured with `fork` instrumented, on a, d and t:

| Measure | Result |
| --- | --- |
| `child_process.fork` in `kill()` | Throws `child_process.fork() is not supported when the runAsNode fuse is disabled; use utilityProcess.fork() instead` |
| Unhandled rejections | One per `kill()`: 103 for 103 kills |
| Without a rejection listener (variants e, g) | No crash; the app runs to the end and exits 0 |
| Relaunches of the exe | 0 |
| `kill()` to exit event | 63–65 ms |
| Grandchild `ping` alive after `kill()` | 0 immediately |
| Grandchild `node` ignoring signals, alive after `kill()` | 0 immediately, at 7 s and at 15 s |

The source (`lib/windowsPtyAgent.js`) calls `fork` for the console process list and then runs the native kill regardless, which is why cleanup still works. The native kill does the work. This covers processes attached to the console; a process that detaches from it was not tested.

**Version.** Measured behaviour is the same on both. The source is not: `src/win/conpty.cc` in 1.1.0 accesses the global `ptyHandles` vector from the JS thread and from per-PTY watcher threads with no lock, which is the race in [#921](https://github.com/microsoft/node-pty/issues/921). Beta.18 has the [#922](https://github.com/microsoft/node-pty/pull/922) mutex around it. The race needs a PTY exit to coincide with a JS-thread call such as `resize`, which is plausible for a long-running terminal, and 100 repeats would not reliably show it. No run crashed on either version, so this rests on the source, not a reproduction.

**How a packaged GUI exe reports results** (`desktop/dist/win-unpacked/VoiceUp.exe --smoke-test`):

| Invocation | Returned after | Result file on return | Exit code |
| --- | --- | --- | --- |
| `& exe` | 16 ms | no; appeared about 300 ms later | none (`$LASTEXITCODE` empty) |
| `& exe \| Out-String` | 394 ms | yes | 0, and stdout was captured |
| `Start-Process -Wait -PassThru` | 1070 ms | yes | 0; 1 on an unwritable path |

Use the result file and `Start-Process -Wait -PassThru`, as `scripts/smoke-test.ps1` does. Piping did capture stdout here, but do not depend on it.

**Reproduce.** `spikes/S0.6/`: `npm install`, `npx install-electron`, then `./run-variant.ps1 -Label x [-Rebuild true] [-Dll] [-RunAsNodeOn] [-NoListener]`, and `node show.cjs x` for a summary. The node-pty version is whichever `package.json` pins (now beta.18), and `electron-builder.yml` holds the trim.

## Environment

Windows 10 Home build 19045, AMD Ryzen 5 3600 (12 logical), 15.9 GiB RAM, no Visual Studio, Python 3.13.2 through `py` only. Node 24.21.0, npm 11.19.0, Electron 45.2.1, electron-builder 26.18.1, node-pty 1.1.0 and 1.2.0-beta.18. CI: GitHub `windows-latest`, Node 24.

## Consequences

- **S1.1:** pin `node-pty` 1.2.0-beta.18; add `npmRebuild: false` and the node-pty excludes to `electron-builder.yml`; add a process-wide `unhandledRejection` handler that logs, and logs this one known message at `debug` so each `kill()` does not read as a fault. PLAN.md S1.1 has these as ACs.
- **S1.3 and shutdown:** `kill()` reached the exit event in about 65 ms, well inside the 2 s budget in TECH_SPEC §3.
- **Trim:** the linux prebuilds in the beta were found after run t, so their exclude is not separately measured. S1.1's packaged smoke test covers it.
- **Moving off the beta:** take stable 1.2.0 when it ships, after the packaged smoke test passes. Re-measure the `kill()` rejection then, because a release may change the `fork` call.
- **Dev machines:** root `CLAUDE.md` no longer lists Build Tools or Python. TECH_SPEC §7.2, PLAN.md and the `native-modules` skill are updated.

## Rejected options

- **`node-pty` 1.1.0:** has the unsynchronized `ptyHandles` access that #922 fixes, and offers no measured advantage.
- **`useConptyDll: true`:** it avoids the `fork`, but failed the typed-output check on 1.1.0. The default path passes, so it isn't worth chasing.
- **Rebuild on install or at package time:** needs Visual Studio on every dev machine for no measured benefit.
- **Turning the `runAsNode` fuse back on:** would weaken the security baseline, and the helper failed with the fuse on anyway.
