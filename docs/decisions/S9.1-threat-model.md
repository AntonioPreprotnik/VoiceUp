# S9.1 — Which device keys, which minimum Android version, and what must v1.2 defend before streaming code?

Date: 2026-11-09 · Status: needs-follow-up (check friends' Android versions before S11.1)

## Decision

Device keys are **ECDSA P-256** on both PC and phone, and the Android app's minimum is **Android 11 (API 30)**. The threat model is `docs/threat-model.md`. Antonio reviewed it on 2026-11-09: he **parked** the stolen-phone protections (`docs/ideas.md`), and widened the phone from view-only to **voice plus a fixed list of actions** (S12.5).

## Evidence

This is a design and platform question, so the evidence is published platform facts checked on 2026-11-09, plus the project's own recorded hook fixtures. Nothing was measured on a device.

| Option                      | Result     | Notes                                                                                                                                                                                                                                                                                                              |
| --------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ECDSA P-256 (SHA-256)       | **Chosen** | In Android Keystore since Android 6 (API 23), hardware-backed on most phones. Built into Node `crypto` in Electron main. The default for WebRTC's DTLS certificates, so one algorithm covers device keys and fingerprint signatures. DER signatures on both sides                                                  |
| Ed25519                     | Rejected   | Arrived in Android Keystore later, through KeyMint 2, and depends on the phone's secure hardware (AOSP `AndroidKeyStoreKeyPairGeneratorSpi` changes). No published API level found that guarantees it across friends' phones                                                                                       |
| Minimum Android 11 (API 30) | **Chosen** | About 90% of active devices (Android Studio numbers, October 2026: 11 is 10.5%, 12 is 9.6%, 13 is 11.8%, 14 is 15.3%, 15 is 14.7%, 16 is 25.4%, 17 about 1%). API 30 adds `AUTH_BIOMETRIC_STRONG` and `AUTH_DEVICE_CREDENTIAL` for `setUserAuthenticationParameters`, which the parked stolen-phone idea would use |
| Minimum Android 10 (API 29) | Fallback   | Only if a friend's phone needs it. Android 10 no longer gets security updates                                                                                                                                                                                                                                      |
| Minimum Android 13 (API 33) | Rejected   | About 68%, which would likely lock out a friend for no gain with P-256                                                                                                                                                                                                                                             |

Threat model coverage (AC1): six attackers, each with mitigations and the story that builds them. These are a stolen phone (parked), a compromised server, the network, the PC's network or local apps, other phone apps, and abuse of the server. AC2's stolen-phone analysis is written and then parked by Antonio. AC4: reviewed by Antonio before any E10 code, on 2026-11-09.

The recorded hooks already carry Claude's `permission_mode` (for example `desktop/test/scenarios/agent-permission-send.json`). The parked idea of refusing phone voice in `bypassPermissions` can rely on that field if it comes back.

## Consequences

- **S9.2:** ECDSA P-256 keypairs, the PC's in `safeStorage` and the phone's in Android Keystore, non-exportable.
- **S9.4, S8.2:** sign and verify with ECDSA P-256 / SHA-256, DER-encoded. Share test vectors between Kotlin and TypeScript through `protocol/`.
- **S11.1:** `minSdk 30`. Check friends' phones first, and drop to 29 only if one needs it.
- **S11.2:** the app exports nothing that starts a session; `voiceup://pair` only opens the pairing screen.
- **S11.3:** `FLAG_SECURE` on the viewing screen.
- **S12.5 (new):** `sendNow`, `reArm`, `windows.list`, `window.focus`, `tab.next` and `tab.prev` are the only phone actions. There's no free text, no arbitrary keys and no mouse.
- **Parked** in `docs/ideas.md`: a Keystore key needing biometric or PIN every 5 minutes, refusing phone voice in `bypassPermissions`, the auto-allow warning and the install-guide advice.
- **TECH_SPEC:** §9.6 already records P-256 and API 30. §11's question "Ed25519 or P-256 for device keys" is answered in this commit.

## Rejected options

- **Ed25519:** Keystore support depends on the phone's hardware, and it brings nothing P-256 doesn't for two-party signatures.
- **Minimum Android 13:** shuts out about a third of phones for no security gain with P-256.
- **Stolen-phone protections now:** Antonio's call. Not worth the time before the phone companion works end to end (`docs/ideas.md`).
- **Strictly view-only phone:** Antonio wants to send, re-arm and switch windows and tabs from the phone. Those go in as fixed actions (S12.5), not as free input.
