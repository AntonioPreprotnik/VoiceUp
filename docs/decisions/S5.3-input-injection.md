# S5.3 — What is the robust way to type voice text into Claude's prompt?

Date: 2026-11-04 · Status: decided

## Decision

Write the text as one bracketed paste, then Enter as a separate write **250 ms** later. Before that, in this order: remove control characters and ESC, collapse newlines, trim, and put **a space in front of text that starts with `/` or `!`**. Text over **900 characters is blocked, never cut**.

Then check what arrived: `UserPromptSubmit`'s prompt must contain the text. This matters because the limits below come from how Claude reads its input, and could move in a later version.

TECH_SPEC §4.5 had a 30 ms delay, a 4,000 character cap, a 3 s confirmation timeout and no guard on the first character. All four were wrong.

## Evidence

129 real sessions, each fresh, with `node spikes/S5.3/run.mjs <output folder> <project folder> [cases]`, which compares the hook's prompt with what was sent. Counts are small, so they show what fails, not a failure rate.

### Method and delay before Enter

Text of 111 characters, with quotes, `$`, `%`, `&`, `<`, Croatian letters, Japanese and an emoji:

| Method | Reached Claude intact | Notes |
| --- | --- | --- |
| Text and Enter in one write | 0 of 1 | Stays in the prompt. A 28-character text did pass, so short tests hide this |
| Paste and Enter in one write | 0 of 1 | Same |
| Paste, Enter 10 ms later | 1 of 1 | |
| Paste, Enter 30 ms later | 20 of 22 | **Enter is lost twice:** the text sits in the prompt, unsent |
| Paste, Enter 100 ms later | 9 of 9 | |
| Paste, Enter 250 ms later | 8 of 8, plus every size test below | Chosen, since waiting costs nothing here |

Paste beats typing because S2.1 found pasted text does nothing in Claude's menus, while typed letters and digits act as shortcuts there.

### Length: text is lost past about 1 KB

| Characters | Result, Enter at 250 ms unless noted |
| --- | --- |
| 200, 500, 800 | Whole and unwrapped (at 30 ms) |
| 900, 1000, 1023 | Whole by length, 3 of 3 each. Wrapped in `<pasted_content>`. Contents compared at 1000: intact |
| 1024 | Right length 3 of 3, but **a fourth run came back one character longer with the contents changed** |
| 1100 | **Lost its first 1024 characters, 3 of 3: 76 left, and submitted** |
| 1500 | Lost 1025 (at 30 ms), and submitted |
| 4000 | **Lost its first 3072 and was submitted, in 6 of 21 runs across delays and methods.** Of the rest, 11 stayed unsent and 4 arrived whole |

Losing the start is the worst outcome for a voice tool: "don't delete the database" would arrive as "delete the database", and be sent. The limit counts characters, not bytes: 800 Croatian characters (1109 bytes) arrived whole.

| Sending long text in pieces | Result |
| --- | --- |
| 512-character writes in one paste, 2000 characters | Whole 2 of 3, **lost 1024 once** |
| Same, 4000 characters | Whole 1 of 3; in the other 2, one character too many |

So pieces don't fix it. Speech doesn't need it: S4.4's 15 s of speech was about 35 words, so the 60 s recording limit is about 140 words, or some 800 characters. Only very fast or very long speech reaches 900.

### What the first character does

| Text sent | Result |
| --- | --- |
| `/clear` | **Runs the command.** The session is cleared |
| `/help me with this` | **Opens the help menu** |
| `/nosuchcommand please` | "Args from unknown skill" |
| `!echo spike-bang` | **Runs in a shell.** No `UserPromptSubmit`, and Claude then responds to its output |
| ` /clear`, ` /model haiku`, ` !echo spike-bang`, with a space first | **Plain text,** exactly as sent |
| `#`, `@`, `?`, `&`, a word containing `/clear` | Plain text |

Speech models rarely start with these, but a misheard or unusual one must never run a command.

### Other findings

| Check | Result |
| --- | --- |
| Paste end marker inside the text, `…\x1b[201~\rSecond` | **Breaks out:** the part before it is submitted, and `Second` stays typed in the prompt. Removing ESC is essential |
| Half-typed text, then paste and Enter | **They merge and are sent:** "half typed Reply with…". No hook or setting shows the prompt's contents, so only prompt-dirty tracking can prevent it |
| Newline inside a paste | Kept. Collapsed anyway, as speech has no use for it |
| Trailing space | Removed by Claude, so the sanitizer trims first and the check still matches |
| Sent while Claude is busy | Claude queues it, and it arrives whole later as its own turn |
| Enter to `UserPromptSubmit` | Median 86 ms, but **up to 4.3 s: 7 of 31 runs took over 500 ms**. Cause unknown. S2.1 saw only 30–80 ms |

**Wrapper:** from somewhere between 800 and 900 characters, the prompt is `\n\n<pasted_content id="…">\n` + text + `\n</pasted_content id="…">\n`. A long real delivery looks like this, so the confirmation has to look for the text inside it.

## Environment

Windows 10 Home 19045, Ryzen 5 3600. Claude Code 2.1.318 through `claude.cmd`, Haiku 5.5. Node 24.21.0, `node-pty` 1.2.0-beta.18, ConPTY, in plain Node rather than Electron. The path to Claude's input is the same `node-pty` write.

## Consequences

- **S5.4:** implements §4.5 as corrected here, including `TRANSCRIPT_TOO_LONG` and `DELIVERY_GARBLED`, and needs the prompt-dirty tracker from §4.4, which nothing builds yet.
- **S5.4:** a lost Enter leaves the text in Claude's prompt, so `DELIVERY_UNCONFIRMED` must say so, and the prompt counts as dirty until the user deals with it.
- **S2.4:** a slow `UserPromptSubmit` can arrive after the 1 s `localUiSuspected` wait, so a real send can briefly show Paused. It recovers by itself, since `unknown` plus `UserPromptSubmit` goes to `busy`.
- **Re-measure on each Claude upgrade.** These limits are not documented behaviour.
- Copied into TECH_SPEC §4.5, §6.5 and PLAN.md S5.3 and S5.4.

## Rejected options

- **Typing the text instead of pasting.** In a menu that S2.4 missed, typed letters and digits act as shortcuts.
- **Text and Enter in one write.** Enter is swallowed once the text is more than a few words.
- **Cutting long text to fit.** It would send a command the user didn't say.
- **Sending long text in pieces.** It lost text in testing.
- **Reading the screen to see if the prompt is empty.** §4 rules out screen parsing.
- **Pressing Enter again if it seems lost.** If the first one was only slow, up to 4.3 s here, a second one could answer whatever appeared next.
